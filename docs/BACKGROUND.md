# Saviu：项目背景

> HackUTD 2026 Zero Day · 赛道：State Farm "The Worst Day, at Scale" + Spacetime "Build with Spacetime"
> 本项目没有使用真实客户数据。地理、人口普查、学校和设施、地震情景是真实的公开数据；所有住户、投保人、灾害事件和结果都是合成的，飓风是假想的，Harbor Bend, TX 是虚构的。

## 一句话
灾害发生时，Saviu 把三种不完美的数据按可信度融合，生成一张实时的 P0 / P1 / P2 地图，告诉 State Farm 的理赔团队先去哪里、还有谁没联系上；理赔员每回传一次现场结果，判断就更准一点。

**English:** When a disaster hits, Saviu fuses three imperfect signals into a live P0–P2 map of which State Farm customers need help first and who we haven't heard from yet, and every field report makes the next decision more accurate.

## 问题
- 大灾之后，报案在短时间内暴增，理赔团队的人手有限，必须决定先去哪里。
- **最吵的地方不一定受灾最重。** 道路和基站断了，受灾最重的家庭可能根本联系不上我们。
- 设计灵感来自 2008 年汶川地震：道路和通信受损，受灾最重的地方反而最安静。我们的原则是：**沉默不等于安全。**

## 用户
| 用户 | 需要什么 |
|---|---|
| State Farm 灾害理赔主管 | 一张实时地图：哪里最紧急、哪里信息不够，人手怎么派 |
| 外勤理赔员 | 手机上的任务列表，现场一键回传"人身安全"和"房屋损坏" |
| 投保人 | 收到简短的短信问候，几秒钟就能回复自己的情况 |

## 方案
**三种数据来源**
| 来源 | 告诉我们什么 | 弱点 |
|---|---|---|
| 1. 灾害强度 + 人工标注的受灾区 | 哪里"可能"受灾 | 只是估计，不知道每户的实际情况 |
| 2. 短信问候（只发给保单地址在灾区的现有客户） | 投保人自己报告是否安全、房子损坏多严重 | 有人夸大或低估；断网的人回复不了 |
| 3. State Farm 自己的数据 | 保单位置、保障范围、实际报案量和应有报案量的差距 | 报案来得晚；沉默的区域报案也少 |

**两个维度分开输出**（按 H3 六边形网格）
- **行动优先级 P0 / P1 / P2**：需要多快采取行动。
- **信息状态 已核实 / 待核实**：信息够不够。一个格子可以是"疑似 P0 · 待核实"。
- 灾害强度高、基站中断、又没有回复的区域，**永远不会**被当成安全。

**各等级的动作**（24 和 72 小时只是产品里的模拟调度目标，不是 State Farm 的服务承诺）
| 等级 | 动作 |
|---|---|
| P0 | 立即提示人身危险，转交当地应急机构；优先联系客户；审核临时住宿支持的资格 |
| P1 | 安排上门查勘（模拟目标 72 小时内） |
| P2 | 引导客户自助报案、上传照片 |
| 待核实 | 优先派人核实，不默认归为 P2 |

**保障范围感知**：每户都带有风灾保障、洪水险、地震附加险的标记。损失不在承保范围内的家庭，同样会被联系，并转介 FEMA 等外部援助资源。

## 模型
- **离线校准**：先用合成的历史事件做回测：Harbor Bend 10 场（每场 3,000 户），Corpus Christi 8 场、Bay Area 5 场（每场 15,000 户），全部带真实结果，按地区分别训练两个逻辑回归：P(严重受损) 和 P(需要帮助)，并检查校准程度（Brier 分数、ECE）。
- **实时推理**：新的风暴来了，模拟器持续产生短信回复、报案和现场报告，引擎实时更新每户和每个格子的估计。
- **学习循环**：
  - 一次现场报告，只立刻更新这一户和所在格子的不确定性。
  - 数据源的可信度权重，要累积多条反馈后小步调整（比如每 10 条一次，有学习率上限）。
  - 留出一组家庭只做评估、永不训练，演示时展示已核实覆盖率和留出集上的真实误差。
- **主动查勘**：派单同时看"可能多严重"和"有多拿不准"，先去最需要核实的地方。

## 为什么用 Spacetime
- 短信回复、报案、现场报告三路数据实时写入；主管看板、理赔员手机、投保人回复页三端实时同步。
- 事件写入、权限检查（只有理赔员能提交现场报告）、融合计算和实时统计，都在 Spacetime 的服务端函数里运行，前端只订阅结果。
- 满足赛道要求：公开 GitHub 仓库，后端大部分基于 Spacetime。

## 隐私和合规
- 只联系现有客户，用的是保单上登记的手机号。真实群发前要核对短信同意和相关规则；演示一律用模拟短信。
- 不追踪陌生人的手机位置。无线紧急警报（WEA）由 FEMA 的 IPAWS 系统管理，发送方需要经过授权，State Farm 不能默认使用。
- 医疗设备等敏感信息只在客户主动提供并同意时使用。
- 人身危险转交公共应急机构，State Farm 不扮演救援队。

## 与评分的对应
| 赛题要求 | 我们怎么回应 |
|---|---|
| 找出需求最紧急的人 | P0 / P1 / P2 + 需要帮助的概率 |
| 协调援助 | 两个队列、理赔员派单、转交应急机构、转介外部援助 |
| 确保没人被遗漏 | 沉默区标为"待核实"，主动查勘优先去拿不准的地方 |
| Spacetime：实时、多人 | 三端实时同步，核心逻辑跑在服务端函数里 |

## 不做的
真实发短信、真实保单系统对接、真实 FEMA 数据训练（放进路线图）、登录系统（用切换角色代替）、深度学习模型。
