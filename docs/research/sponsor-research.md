**为什么首选 War Room**（评委团调研员把它排第 4，我把它提到第 1，理由如下）：
- 题目要求的每一项都能在现场被验证：篡改报警、服务器只能看到密文、通行密钥（passkey）登录。评委不用相信我们的话。
- 不依赖数据质量和模型准确率，而 State Farm、T-Mobile、CBRE 在 20 小时里最大的风险恰恰是这两样。
- 律所视角是多数队伍想不到的深度：数据范围决定通知期限，"由谁、何时认定"的时间戳决定 SEC 时限从何时起算，保密特权决定谁能看什么。
- 和团队的 Web 全栈加实时同步能力最匹配，也最贴 Zero Day 主题。
- 缺点：情感冲击不如灾害题，"AI"成分少。如果团队更想做社会影响或 AI，选第 2 名。

## 四、首选方案：War Room 执行手册

**一句话**：在公司网络之外独立运转的网络事件指挥台。律师和应急团队在这里记录事件、界定被泄露的数据、按法定时限推进；即使攻击者控制了全部内网，这里依然可信。

**演示（90 秒）**
1. 评委扫码，用通行密钥以"外部律师"身份加入。邀请码是一次性的，还要和管理员线下口头核对。
2. 评委把"文件服务器 PHI：Unknown"改成"已外泄 1,200 条"。所有人的屏幕同步刷新，HIPAA 和 3 个州的倒计时亮起，系统生成通知清单，时间线写入"由谁、何时认定"。
3. 另一位评委扮演"已拿到管理员权限的攻击者"，直接在数据库里改一条记录。点"验证链"后变红，并定位到被篡改的条目；服务器视角只能看到特权频道的密文。
4. IT 人员打开取证草稿时被拦下，请求转给律师批准，系统写入分发台账。

**技术深度**
- 安全：WebAuthn 通行密钥、哈希链加 Ed25519 签名的审计日志、只在客户端做的加密（特权频道用线下口令经 PBKDF2 派生密钥）、最小权限。
- 法规引擎：数据范围表（系统 × 数据类别 × 州 × 状态：已加密 / 已外泄 / Potentially / Unknown）对应各法域的时限。已核实的规则有：德州 250 名以上州民受影响时，30 天内报总检察长，个人通知 60 天；SEC 在认定重大性后 4 个工作日内披露。HIPAA 和 GDPR 的时限要上场前核对。
- 压力下的易用性：大按钮、"下一步做什么"清单、零教程。
- 可选的 AI：用户用自然语言描述情况，系统转成结构化事件记录；也可以根据数据范围起草通知信（只起草，由律师审）。

**4 人分工**
| 人 | 负责 |
|---|---|
| 1 | 安全：通行密钥、邀请和核对码、哈希链、签名、特权频道加密 |
| 2 | 实时后端：Spacetime 表（事件、时间线、数据范围、消息、成员）。16:00 还没跑通就换 Supabase Realtime |
| 3 | 法规引擎 + 合成事件（虚构德州牙科连锁遭勒索：72 小时时间线、10 个系统的数据清单） |
| 4 | 压力模式界面、演示脚本、Devpost、演讲 |

**时间点**
- 13:30 定方向，在 Devpost 建项目，写好 90 秒演示脚本
- 15:00 骨架部署上线：登录、实时聊天、事件表
- 20:00 主流程跑通：数据范围 → 倒计时 → 时间线 + 哈希链
- 23:00 交 Devpost 初稿
- 夜间：特权频道加密、权限审批、界面打磨

**降级方案**：端到端加密只做特权频道；法规只做德州、SEC、HIPAA 三条；砍掉视频通话、移动端、SSO 和全量 50 州法规。

**评委最可能追问**
1. 邮箱和域控都失陷时，怎么安全地邀请新成员？（答：线下口头核对码 + 通行密钥）
2. 托管方或服务器被攻破怎么办？（答：特权内容只在客户端加密；哈希链能发现篡改）
3. 成员的设备失陷，怎么吊销？（答：管理员撤销该通行密钥，相关密钥轮换）

## 六、补充：NMC² "Keep the World Running"

> 这一节是我根据赛题截图做的分析，没有派调研员，引用的事实没有逐条重新核实。

**题面**：每个 AI 模型、流媒体和云应用背后，都有一个数据中心和一支 24 小时值守的团队。漏掉的告警、不清楚的交接、在错误时刻拿到错误的信息，都可能让小问题变成大事故。NMC² 要我们帮数据中心团队"领先一步"。
奖品：AirPods Max Gen 2 / Apple Watch Series 12 / Echo Show 11。工作坊：周六 16:20–17:05。

**真正想要什么**：题面点名了三种失误：漏掉告警、交接不清、信息错位。最好的作品要证明能分别拦住这三种失误，而不只是做一个监控大屏。

**现有方案**：DCIM 软件（Schneider EcoStruxure IT、Vertiv、Nlyte、Sunbird）管设备和容量；PagerDuty、ServiceNow 管告警和工单；Grafana 做可视化。缺口是这些系统之间的断点：告警不知道会影响哪些客户，换班交接靠口头和聊天记录，现场技术员拿不到"这台设备此刻能不能动"的信息。

**数据**：全部可以合成。建一个小型数据中心模型（2 个机房、20 个机柜、2 台冷水机组、4 台精密空调、2 台 UPS），写一个遥测模拟器。可以用来增加真实感的公开数据：[LBNL 故障检测数据集](https://faultdetection.lbl.gov/data)（含冷机房数据）、[Alibaba GPU 集群 trace](https://github.com/alibaba/clusterdata)、[Google 集群 trace](https://github.com/google/cluster-data)。讲背景可以引用 [Meta Llama 3 论文](https://arxiv.org/abs/2407.21783)：54 天训练中出现 419 次意外中断，约 78% 归因于硬件问题。

**三个方向**
1. **告警 → 影响图**：依赖图沿两条链展开，供电链是市电 → UPS → PDU → 机柜，制冷链是冷水机组 → 精密空调 → 机柜，再往下到 GPU 节点 → 正在跑的任务 → 客户。演示：注入"冷水机组降级" → 200 条告警收敛成 1 个事件 → 显示"C 排机柜 11 分钟后到 35°C，影响 512 块 GPU 和 3 个客户任务"。
2. **不掉棒交接**：换班时，每个未闭环事项都必须由接班人明确接手；系统列出"你离开后发生了什么"。LLM 从聊天里抽取待办，再和遥测数据核对。
3. **现场防误操作**：技术员扫机柜二维码，只看到与这台设备相关的信息。如果他要断电的 PDU 正好是另一路已经告警的冗余电源，系统直接拦下，并给出安全的操作顺序。

**推荐的演示（三幕对应三种失误）**：凌晨 3 点冷水机组缓慢劣化（漏掉告警）→ 7 点换班（交接不清）→ 白班技术员准备维护错误的 PDU（信息错位）。系统在三个时刻各拦一次，并显示"如果没拦住，会损失多少 GPU 小时"。

**可行性（1–5）**：设施模型和模拟器 3；告警收敛与根因定位 3；热模型和倒计时 3；交接协议 2；扫码现场页 2；LLM 交接摘要 2。最难的是让模拟出的物理过程在懂行的评委面前可信。降级方案：只做一条预先录好的故障剧本，参数全部公开在页面上。

**评委视角**：最可能看到的同质化作品是 Grafana 式大屏、"和日志聊天"、拿随机 CSV 做异常检测、LLM 写的交接摘要。能让评委眼前一亮的是告警数量当场从 200 条变成 1 条、到达温度阈值的倒计时、危险操作被拦下。最可能追问：依赖图从哪来（DCIM 导入还是自动发现）？误报多少？怎么接入 ServiceNow 或 PagerDuty？

**组合**
- **NMC² + CBRE（强）**：CBRE 本身也做数据中心设施管理，题面的"预测故障、量化影响、提前处置"和 NMC² 完全对得上。同一个依赖图引擎，给 CBRE 评委从楼宇设施讲起，给 NMC² 评委从 GPU 和客户任务讲起。稀释风险低。
- **NMC² + Winstead（弱）**：能共用"指挥台"的外壳，但一边是运维、一边是网络安全和法律，评分标准差别大。

**打分**：深度 4 / 评委兴趣 4 / 可行性 4 / 数据易得性 3。**NMC² + CBRE 组合可以替换 Aftershock，成为第 2 名**；团队更偏向基础设施和 AI 的话，可以选它当主方向。

## 七、灾后诈骗的规模（演讲用数据）

**Google 结果数不能用**：2026-11-07 实测，"disaster scam" 约 361 条，"disaster scams"、"disaster fraud"、"FEMA scam" 加引号后都只有 57–59 条。Google 现在显示的只是它实际返回的去重结果数，不是索引里的总量，所以无法用来衡量问题规模。

**可用的估算**（NICB：巨灾损失中最多约 10% 流向灾后诈骗）

| 口径 | 巨灾保险损失 | × 10% = 诈骗损失上限 |
|---|---|---|
| 2021 年美国（NICB 原数） | $92B | $9.2B |
| 2024 年美国（Swiss Re 全球 $141B × 约 80%） | 约 $113B | 约 $11.3B |
| 2025 年美国（Gallagher Re） | $100B | $10.0B |
| 2025 年美国（Swiss Re） | $89B | $8.9B |
| 2025 年洛杉矶山火单一事件（Gallagher Re） | 约 $41B | 约 $4.1B |

- 结论：美国每年约 **$90–110 亿** 流向灾后诈骗。平摊到每天约 $2,700 万，但诈骗集中在灾后几周，实际峰值远高于均值。
- 投诉量：NCDF（国家灾害欺诈中心）自 2005 年起累计收到 22 万多件投诉，平均每年约 1.16 万件；其中仅卡特里娜飓风就有 30,110 件，约占 14%，分布极不均匀。2017 年的一则报道称，巴吞鲁日在飓风 Harvey 前一周有 79 件报告，后一周有 425 件，约为 5.4 倍（来自搜索摘要，未打开原文）。
- 注意：NICB 的金额主要是保险理赔欺诈（含承包商虚报），NCDF 统计的是投诉件数，两者口径不同，不能相除得出"每件投诉的损失"。

## 八、State Farm 修正版：灾后客户关怀指挥台

**定位修正**：State Farm 是保险公司，不指挥救援队进村。产品改成服务它自己的灾害理赔团队（CAT team）、代理人和理赔员："没有报案"不等于"没有受灾"。

**核心逻辑**
- **沉默分**：按灾害强度和保单分布，每个区域"应有多少报案" − "实际收到多少报案"，再用断路、断网情况修正。
- **分流**：
  - 人身危险：转交 911 和公共救援机构，并记录"已转交"。
  - 房屋或车辆受损：派给外勤理赔员或代理人。
  - 房子无法居住：优先联系客户，审核临时住宿支持（额外生活费用）的资格。是否能获得，取决于损失是否在承保范围内、具体保单怎么写。
  - 没有洪水险：提示可以申请 FEMA 等外部援助。
- **跟踪**：每户的联系状态、负责人、下一步、联系失败的次数。失败超过 N 次自动升级，比如改派代理人上门。
- **隐私**：只用客户主动提供的信息。把投保人信息转给公共机构，需要有客户同意或法律依据。

**演示瞬间**
1. 理赔主管的地图上，3 万户虚构投保人里，有 412 户处在震感或水淹最重的区域，却没有报案、也联系不上。
2. 系统按"受灾强度 × 房屋状况 × 家庭脆弱度 × 道路和通信中断"排序，并把上门任务按路线派给 6 位理赔员。
3. 理赔员在手机上标记"已上门：房屋无法居住"，主管的地图实时变色，系统把这户加入"审核临时住宿支持资格"的待办。

**训练和回测数据**：OpenFEMA 国家洪水保险的理赔数据是真实的保险理赔（带普查区和损失日期），最适合用来学"某种强度下应有多少理赔"。投保人、报案流、联系记录全部用虚构数据。道路孤岛（OSM）、通信中断（FCC DIRS）的用法和第七节一样。

**赛道**：State Farm + Spacetime。理赔主管、理赔员、代理人多端实时同步，正好是 Spacetime 擅长的。

**评分**：8.5。

## 九、团队方案：三源融合 + 现场反馈，划分 P0 / P1 / P2

> 本节已被第十节修正：P0 的服务承诺、队列结构和学习方式都以第十节为准。

**想法**：灾害发生时，AI 按可信度融合三类数据，把灾区划成 P0 / P1 / P2；理赔员到现场后回传真实情况，模型越用越准。

**三处修正**
1. **"救援团队"改成 State Farm 的外勤理赔员。** 人身危险转交 911。
2. **不要用 GPS 定位陌生人的手机。** 改成按保单地址，给本身就在灾区的投保人发短信："1 安全无损 / 2 房屋受损 / 3 无法居住 / 4 有人身危险"。App 用户在授权后可以附带位置。
3. **没回复不等于没事。** 灾害强度高、通信中断、又没回复的区域，要升级处理，而不是归为 P2。

**模型（按 H3 六边形网格计算）**
- **先验**：灾害强度 + 人工标注的受灾区域。
- **证据**：短信回复（严重回复的比例、回复率）、报案量和"应有报案量"之差。
- **融合**：按每个数据源的可信度加权，输出严重程度和置信度。
- **学习**：理赔员回传的现场结果当真实标签。每回来一条，就更新各数据源的可信度权重和校准。比如发现某区的短信自报系统性偏高，就调低这个区短信的权重。
- **主动查勘**：派单不只看"最严重"，也看"最不确定"。到不确定性最大的地方去查勘，模型学得最快。

**P0 / P1 / P2**
| 等级 | 含义 | 动作 |
|---|---|---|
| P0 | 很可能房屋无法居住或有人身危险 | 人身危险转 911；24 小时内派理赔员；预付额外生活费用 |
| P1 | 很可能有明显损失 | 72 小时内上门查勘 |
| P2 | 损失轻微 | 客户自助报案（上传照片） |
| 待核实 | 沉默、置信度低 | 优先派人查勘，不默认归为 P2 |

**演示**：短信回复和报案实时涌入，地图上的六边形不断变色 → 理赔员在手机上回传"已查勘：严重" → 周边区域重新评级，可信度权重面板跟着变 → "准确率曲线"随现场反馈上升（这条曲线是在已知真实答案的模拟数据上算的，演讲时要说明）。

**赛道**：State Farm + Spacetime。短信回复、报案、现场回传三路实时流加多端同步，正好是 Spacetime 擅长的。

## 十、修正版（以此为准）

**1. 场景定位**
- 汶川只作为设计灵感："道路和通信受损时，受灾最重的地方最安静。"演示设在**虚构的美国灾区**。
- **只选一种灾害，并在数据里标明保障范围。** 普通房屋险通常不保洪水和地震，需要单独的洪水险或地震附加险。建议用飓风：风灾通常在房屋险的保障范围内，洪水要看有没有洪水险，正好展示"按保障范围分流"。每户都带上 `风灾保障 / 洪水险 / 地震附加险` 三个标记。
- 不在承保范围内的损失，转介 FEMA 等外部援助资源。

**2. 不做服务承诺**
- P0 的动作改成："立即提示人身危险，转交当地应急机构；优先联系客户；审核临时住宿支持的资格。"
- 24 小时和 72 小时只作为产品里的"模拟调度目标"，不说成 State Farm 的承诺。

**3. 两个维度分开**
| 维度 | 取值 | 含义 |
|---|---|---|
| 行动优先级 | P0 / P1 / P2 | 需要多快采取行动 |
| 信息状态 | 已核实 / 待核实 | 信息够不够 |

一个格子可以同时是"疑似 P0 · 待核实"。理赔员表单和短信也分开记录两件事：
- **人身安全**：安全 / 需要帮助 / 不确定
- **房屋损坏**：无 / 轻微 / 严重 / 无法居住

**4. 学习方式**
- **局部更新**：一次查勘只立刻更新这一户，以及所在格子的不确定性。
- **全局更新**：数据源的可信度权重，要等累积多条反馈后小步调整，比如每 10 条更新一次，并设学习率上限。
- **评估**：主动查勘会偏向难判断的地区，所以要留出一组不参与训练的模拟家庭专门做评估。
- **演示里展示的指标**：已核实覆盖率（P0 嫌疑户中已联系或已核实的比例），加上留出集上的真实误差。误差会波动，如实展示，不承诺曲线一直上升。

**5. 18 小时的优先级**
- **23:00 前必须跑通主闭环**：模拟事件 → 地图分级 → 理赔员回传 → 地图和待办更新。同时交 Devpost 初稿。
- **其后**：可信度在线学习、评委扫码回复、指标图表。
- **Spacetime 赛道的要求**：事件写入、权限检查、核心融合逻辑都要真正运行在 Spacetime 后端（服务端函数），不能只把它当消息通道。

**6. 隐私表述**
- 不说"只有政府能发区域广播"。准确的说法是：无线紧急警报（WEA）由 FEMA 的 IPAWS 系统管理，发送方需要经过授权，State Farm 不能默认使用。
- 产品设计是按保单地址联系现有客户。真实群发前还要核对短信同意和相关规则；本次演示一律用模拟短信。
