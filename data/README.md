# Triage Loop synthetic data

> **Everything in this folder is synthetic.** Harbor Bend, TX, the other towns, the storms and every household are made up. The coordinates only put the fictional grid somewhere on a basemap. No real customer, policy, hazard or claims data was used.

Generated by `sim/` (`npm run sim`). The format is the `EventBundle` type in [`shared/types.ts`](../shared/types.ts).

| File | Contents |
|---|---|
| `live.json` | Live demo event `live`, "Harbor Bend, TX". `sms_sent`, `sms_reply` and `claim` events, but **no `field_report`** (adjusters create those during the demo). `truth` is included only so the demo can score the holdout households. |
| `backtest/backtest-1.json` … `backtest-6.json` | Six past storms, each in its own world (different seed, center, track, intensity). Full truth, plus `field_report` events for about 10% of households. |
| `sim-meta.json` | Simulator notes for demo scripting: where the deliberate quirks are, plus the silent-severe cells. **Not part of the contract. The engine must not read it.** |
| `model.json` | Owned by the engine, not by the simulator. |

Total is about 10 MB. A "silent-severe" cell has high hazard (wind ≥ 110 mph or flood ≥ 4 ft), heavy outage (≥ 80%), a reply rate under 10%, and more than 40% of its households truly severe (damage ≥ 2) or needing help.

## File layout
Each file is a single JSON object, `{ world, events, truth }`, with one array element per line so diffs stay readable. Every value is a plain number, string or boolean. Times `t` are **whole minutes after landfall**, from 0 to 4320 (72 h). `events` is sorted by `t`. Ties are broken by kind (`sms_sent` < `sms_reply` < `claim` < `field_report`) and then by householdId.

## Data dictionary and generation model

### World and grid
- H3 resolution 8, `gridDisk(centerCell, 10)` = **331 cells**, sorted by hex id. The live center is lat 28.70, lng -96.20 (`LIVE_CENTER` in `sim/src/config.ts`). Each backtest world has its own center.
- A flat local projection in km is used. **The south edge is the coastline.** `dc` means distance inland from the coast, about 0–17 km.
- Household ids look like `<eventId>-h00001`, so they are unique across all bundles.

### `HexCell`
| Field | How it is generated |
|---|---|
| `windMph` | `40 + (vmax-40)·exp(-|d|/R)·side·inland + N(0,3.5)`, where `d` is the perpendicular distance to the storm track (straight or slightly curved, with a heading of -35° to +28°). `side` is 1 on the right of the track and 0.82 on the left. `inland = 1 - 0.011·dc`. Values run from about 40 to 140 and are rounded to whole mph. |
| `floodDepthFt` | Storm surge `surgeFt·exp(-dc/L)·(0.3+0.7·alongshore)`, highest at the coast just right of the track. On top of that come 3 rain-flooding pockets (Gaussian blobs) and N(0,0.25). Anything under 0.5 ft becomes 0. Rounded to 0.1 ft. |
| `towerOutagePct` | `85·sigmoid((wind-116)/8)`, plus one strong outage cluster on the track near the coast (amplitude 95, radius about 1.7 km), plus 2–3 random clusters (amplitude 45–80) and N(0,4). Clamped to 0–100 and rounded. |
| `analystZone` | A human-style map. It is computed from the **forecast** track, shifted 1–2 km sideways (lag), with no rain pockets or local noise, then averaged over each cell's neighbours (coarse). Score ≥ 1.9 → 2, ≥ 1.0 → 1, otherwise 0. Two deliberate mistakes follow (see Biases). |

### `Household`
About 3,000 per world. Every cell has at least 2. The rest are spread by density weights (3 town centers plus lognormal noise). Each household sits at a random point inside its cell (checked with `latLngToCell`).

| Field | Rate |
|---|---|
| `age65` | 20% |
| `livesAlone` | 25% if age65, otherwise 10% (about 13% overall) |
| `medicalDevice` | 9% if age65, otherwise 2.75% (about 4%) |
| `windCovered` | 97% |
| `floodPolicy` | `0.10 + 0.50·exp(-dc/5)`, about 25% overall and higher near the coast |
| `earthquakeEndorsement` | 5% (display only) |
| `phoneOnFile` | 88% |
| `holdout` | Exactly 15% (450), chosen uniformly at random in every world. **Never train on these.** In backtests they never get field reports. |

### `TruthRow`
- Each household gets its own wind (cell wind × (1+N(0,0.05))) and flood depth (cell depth + N(0,0.8) if the cell is flooded).
- Scores: `w = (wind-60)/26` and `f = depth/2.7`, each plus N(0,0.35) noise. `sev = max(w,f) + 0.25·min(w,f) + vulnerable(6%: +0.7) + N(0,0.3)`.
- `damage`: sev < 1.0 → 0, < 1.8 → 1, < 2.6 → 2, otherwise 3.
- `peril`: `'none'` if damage is 0. Otherwise `'flood'` if f > w, else `'wind'`.
- `safety`: needs_help with probability `sigmoid(-4.6 + 1.9·[d=3] + 0.8·[d=2] + 0.5·age65 + 1.2·(age65∧alone) + 1.8·(medical∧outage>60) or 0.5·medical + 0.6·[depth>4])`. That works out to about 1.5–5% of households, depending on the storm.

### Events
| Kind | Generation |
|---|---|
| `sms_sent` | Every household with `phoneOnFile`, at t uniform in 60–180. |
| `sms_reply` | `p = 0.78·(1-outage)^1.6`, then ×0.7 if age65, ×0.6 if damage is 3, ×0.5 if needs_help. In live, the reply rate by outage band (0–20/20–40/40–60/60–80/80–100%) is about 65/37/19/11/1%. Delay is lognormal with median `40·(1+20·o²)` min and σ 1.1 (live p10/p50/p90 ≈ 107/178/336 min after landfall). `damage` is truth with ±1 noise (30%) plus the biases below, clamped to 0–3. `safety`: true needs_help → needs_help 85% of the time; true safe → needs_help 3% of the time. |
| `claim` | Probability by damage 0/1/2/3 is 0.03/0.35/0.75/0.9. It is ×0.15 for a flood loss without `floodPolicy` and ×0.2 for a wind loss without `windCovered`. `peril` is the truth peril; for damage 0 it is the cell's dominant hazard. Delay is `30 min + lognormal(median 8h·exp(3·o²)·(1+0.3·damage), σ 0.8)`, so heavy-outage and severe households file much later. In live, claims arrive at p10/p50/p90 ≈ 5.6 h / 15 h / 49 h. `reportedDamage` is truth, +1 with 15% probability and -1 with 10%. |
| `field_report` | Backtests only. A random 12% of **non-holdout** households (306 per world), at t uniform in 1440–4320, from `adj-01`…`adj-10`. `damage` equals truth. `safety` equals truth, except 6% are `'unsure'`. |

Any event with t > 4320 is dropped. That is how the "claims vs expected claims" gap shows up: heavy-outage areas have expected claims that have not arrived yet.

## Deliberate biases (what the engine has to cope with)
1. **Silence is not safety.** The strongest outage cluster sits on the track near the coast. Replies there are close to zero, claims are delayed past the horizon, and the households are the most severely hit. Needs-help and damage-3 households reply less often, even where there is signal.
2. **Analyst under-marked a hard-hit cluster.** One radius-2 cluster (19 cells) of high-hazard cells, at least 3.5 km from the track outage center, is forced down to zone 0 or 1. In live: center `8848906c13fffff`, where 207 of 254 households have damage ≥ 2 and the zones are 8×0 and 11×1.
3. **Analyst over-marked a safe area.** One radius-2 cluster of low-hazard cells is set to zone 2 (sometimes 1). In live: center `884893d71dfffff`, with 1 of 113 households severe.
4. **Over-reporting district.** In one radius-3 district (37 cells) of moderate hazard, SMS damage gets +1 with 45% probability. In live: center `8848906dc5fffff`, where mean reported minus true damage is +0.45 (elsewhere about 0).
5. **Seniors under-report.** age65 SMS damage gets -1 with 30% probability (mean bias about -0.1).
6. **Analyst zones lag.** Zones come from a forecast track shifted 1–2 km sideways, so they are spatially offset from the real hazard.
7. Flood losses without a flood policy rarely produce claims, so a flooded area that is mostly uninsured for flood looks quiet in claims.

All quirk locations for every world are in `sim-meta.json`.

## Regenerate
```bash
cd sim
npm install
npm run sim        # writes data/live.json, data/backtest/*.json, data/sim-meta.json
npm run check      # validates the contract shape and prints the summary table
npm run typecheck
```
Storm parameters, seeds and centers are in `sim/src/config.ts`. The generation model is in `sim/src/generate.ts`. If you change the model, update the tables above using the `npm run check` output.
